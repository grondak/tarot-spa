# Story 1.1: Redeem an Invite Key to create an Account

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a friend holding a valid Invite Key,
I want to enter my key and create an account,
so that I can start using tarot-spa.

This is Epic 1's first story and the project's first backend story ever — it stands up the entire Amplify Gen 2 backend (Cognito, Data, the post-confirmation function) as its technical foundation. Nothing backend-related exists before this story; everything after it builds on what this story creates.

## Acceptance Criteria

1. **Given** a visitor holds a valid, unredeemed Invite Key, **when** they enter the key and complete Cognito signup, **then** an Account is created with the `generation` inherited from the key, and the key's status flips to `redeemed`.
2. **Given** a visitor enters an invalid Invite Key, **when** they attempt signup, **then** they see "This key isn't valid" and no Account is created.
3. **Given** a visitor enters an already-redeemed Invite Key, **when** they attempt signup, **then** they see "This key's already been used" and no Account is created.
4. **Given** a visitor enters a revoked Invite Key, **when** they attempt signup, **then** they see "This key was revoked" and no Account is created.
5. **Given** two concurrent signup attempts using the same unredeemed key, **when** both submit at nearly the same time, **then** only one Account is created; the other is rejected as already-redeemed.
6. **Given** someone who already has an Account, **when** they attempt to redeem a second Invite Key under the same verified email, **then** the second signup is rejected.
7. **Given** this is the first new screen built for this release, **when** it renders on any viewport, **then** it uses `DESIGN.md`'s dark color tokens (no light mode/toggle), resizes fluidly across desktop and phone with no separate mobile layout, and every input/button carries an associated label and visible focus state.

    1. Read the Invite Key code from `event.request.clientMetadata.inviteKeyCode` — the frontend passes it as `clientMetadata: { inviteKeyCode }` in its `signUp()` call (Task 5). "Rejecting the signup" in practice means deleting the just-confirmed Cognito user as a compensating action immediately after, not preventing confirmation. Don't attempt to throw from the handler expecting Cognito to roll back confirmation on its own — it won't.

### Live Sandbox Findings

Tony ran `npx ampx sandbox` — deployed clean in 73s, no circular-dependency errors, AppSync endpoint live. One real issue surfaced by the deploy output itself:

- [x] [Review][Patch] Amplify's own deploy warning: **"owners may reassign ownership for the following model(s) and role(s): Account: \[owner\]"** [amplify/data/resource.ts:5-16] — plain `allow.owner()` grants the owning user full create/update/delete on their own `Account` record via the GraphQL API, not just read. A signed-in user could have called the Data client directly to rewrite their own `generation` (e.g. escalate `SecondGen` → `FirstGen` to become onward-invite-key-eligible) or reassign `owner` to another user's `sub`. All legitimate writes to `Account` already happen exclusively through the trusted post-confirmation Lambda's direct IAM/DynamoDB access, which doesn't go through this rule at all — so client-side write access was pure unnecessary exposure. Fixed: restricted the owner rule to `.to(['read'])`. Confirm on the next sandbox redeploy (file-watch should pick it up automatically) that the warning is gone.
- [x] [Review][Patch] **The `tableName` override only applies at table *creation*, never on update** [amplify/backend.ts] — verified against the deployed sandbox: the CloudFormation template contains `tableName: 'tarot-spa-tonyreynolds-Account'` (so the Round 2 `addPropertyOverride` fix does reach CFN), and the Lambda's env vars carry the namespaced names, but the physical tables were still `Account-<apiId>-NONE`/`InviteKey-<apiId>-NONE`. Root cause (confirmed in Amplify's table-manager handler source, `@aws-amplify/graphql-model-transformer`): `toCreateTableInput` honors `props.tableName` on CREATE, but the UPDATE path describes the existing table by physical ID and only diffs GSIs/billing/TTL — a changed `tableName` is silently ignored. Superseded by the next finding — custom names turn out to be unworkable even on CREATE.
- [x] [Review][Patch] **Second real signup attempt: Cognito auto-sign-in needs the `USER_AUTH` flow, which Amplify Gen 2's default app client doesn't enable** [src/components/SignUp.jsx] — with the clientMetadata fix in place the backend succeeded fully (key redeemed, Account created), but `autoSignIn()` failed with a 400: the app client's `ExplicitAuthFlows` are only `ALLOW_USER_SRP_AUTH`/`ALLOW_CUSTOM_AUTH`/`ALLOW_REFRESH_TOKEN_AUTH` (verified via `describe-user-pool-client`), and Cognito's auto-sign-in session mechanism requires `USER_AUTH`. Fixed by dropping the auto-sign-in mechanism entirely: after `confirmSignUp()` succeeds, the component calls `signIn({ username, password })` with the credentials already in state — uses SRP (enabled), no session-expiry window, no app-client config dependency. Tests updated.
- [x] [Review][Verified] **Full live verification completed 2026-07-12** — AC1: real browser signup end-to-end (key redeemed with `redeemedBy` set, Account created with `generation: FirstGen` inherited and `owner` = sub, user landed signed-in in the app). AC2–4: exact rejection copy unit-tested + live `checkInviteKey` verified via AppSync (valid → `unredeemed`, bogus → `null`). AC5's compensating-delete path was live-exercised (inadvertently) by the clientMetadata bug: the trigger really did `AdminDeleteUser` a just-confirmed user, and the client showed the honest failure message rather than faking auth. AC6: live-verified (see Task 4). AC7: screen used in anger across the flow.
- [x] [Review][Patch] **First real signup failed: `clientMetadata` must be passed to `confirmSignUp()`, not (only) `signUp()`** [src/components/SignUp.jsx] — live test with a freshly seeded key: Cognito confirmed the user, then the PostConfirmation trigger saw *no* `inviteKeyCode` and took its compensating-delete path (user deleted, key untouched, no Account) — the client then surfaced the honest "couldn't sign you in automatically" message added in Round 2. Root cause: Cognito forwards `clientMetadata` per API call — metadata on `signUp()` reaches only the PreSignUp trigger; the PostConfirmation trigger fires from `confirmSignUp()` and receives that call's metadata. The story's own Task 4 instruction ("the frontend passes it as clientMetadata in its signUp() call") was wrong on this point. Fixed: the invite key now rides along on `confirmSignUp()` as well; component test updated to pin this.
- [x] [Review][Patch] **Custom table names are fundamentally unworkable — the hardcoded-name mechanism is retired entirely, replaced by an SSM parameter bridge** [amplify/backend.ts, amplify/auth/post-confirmation/handler.ts, scripts/seed-invite-key.mjs] — a fresh sandbox deploy (after `ampx sandbox delete`) failed with `CREATE_FAILED` on both tables: *"User: .../AmplifyManagedTableOnEven... is not authorized to perform: dynamodb:CreateTable on resource: ...table/tarot-spa-tonyreynolds-Account"*. Amplify's own table-manager role is IAM-scoped to Amplify's default table naming, so a custom-named `Custom::AmplifyDynamoDBTable` can never deploy. The prior sandbox only ever deployed "successfully" because the override was a silent no-op there. **Redesign:** the actual requirement was never custom names — it was getting the data stack's table names to the auth-stack Lambda without a deploy-time cross-stack reference. Now: (1) the data stack publishes its real (default-named) table names to SSM parameters at fixed plain-string paths (`/tarot-spa/<env>/account-table-name`, `/-invite-key-table-name`) — same-stack refs, no cycle; (2) the Lambda resolves them from SSM once per container at cold start (paths passed as env vars); (3) the Lambda's DynamoDB IAM grant uses plain-string prefix wildcards (`table/Account-*`, `table/InviteKey-*`) plus an SSM read grant on this environment's parameter path; (4) `staging`/`main` collision-avoidance now rests on Amplify's own default naming (which embeds the per-environment AppSync API id) instead of a bespoke mechanism; (5) the seed script now takes the *environment name* (e.g. `tonyreynolds`) and resolves the table name from the same SSM parameter itself — no more manual table-name discovery. Unit tests updated (16 passing, including a new SSM-resolution-failure path test).

**Noted, not fixed (accepted as-is):**
- API key `apiKeyAuthorizationMode: { expiresInDays: 30 }` has no rotation plan — an ops/process concern, not a code defect; new signups' pre-check will start failing 30 days after each deploy unless someone rotates/redeploys.
- Clicking "Back" after a successful `signUp()` leaves the original (mistyped-email) Cognito user unconfirmed indefinitely, still carrying the original invite key's `clientMetadata` — Cognito has no clean "cancel this signup" API; relies on Cognito's own unconfirmed-user expiry.
- `handleSignUp`'s implicit else-path for a `nextStep.signUpStep` other than `CONFIRM_SIGN_UP` is unreachable given the current `defineAuth` config (email verification is always required) — not worth speculative handling for a currently-impossible path.

## Dev Notes

- **The atomic mechanism is the whole point of this story.** AC 1/5/6 all hinge on the post-confirmation trigger's single `TransactWriteItems` call (Task 4). A naive read-then-write implementation (check InviteKey status, then separately update it) reopens the exact concurrent-double-redemption race this story exists to prevent — this was flagged explicitly by an earlier adversarial architecture review and is why the transaction must be one atomic call, not two.
- **Post-confirmation triggers can't block confirmation.** This is the single most likely place to get this story subtly wrong — see Task 4 step 3. Confirmation has already happened by the time the trigger fires; "rejecting" a bad redemption means deleting the just-confirmed Cognito user afterward (`AdminDeleteUser`), not preventing confirmation from completing.
- **Don't build a custom email-uniqueness check.** Cognito's own `loginWith: { email: true }` setting already makes email the unique identifier across the pool. AC 6 is satisfied by that one config line, confirmed via the search backing Architecture AD-16 — this is exactly the kind of "wheel reinvention" this workflow exists to prevent.
- **Don't use the prebuilt Amplify UI Authenticator component.** It has no concept of this project's InviteKey business logic and can't produce the three distinct rejection messages UX-DR9 requires. Build the form directly against `aws-amplify/auth`'s `signUp()` API.
- **No router library.** The existing app has zero routing (confirmed in `project-context.md`); this story extends the same conditional-render pattern `App.jsx` already uses, one level deeper (auth state). Don't introduce React Router or similar as a side effect of adding a second "screen."
- **Data model scope discipline:** only `Account` and `InviteKey` get created in this story. `Session`, `DailyUsage`, `MonthlySpend`, and `Config` belong to Story 3.2 and Story 4.3 — don't scaffold them early "while I'm in here."
- **Testing infrastructure starts here.** No test framework exists in the repo yet; this story is where it gets introduced (Vitest + React Testing Library is the standard, conventional pairing for Vite + React — no existing convention is being broken by picking it).
- **No secrets/env-vars to hand-wire.** `project-context.md` flags "no secrets exist anywhere in this repo" as new territory this story opens up — but Amplify Gen 2's own model handles this: the sandbox/deploy process generates `amplify_outputs.json` (Cognito pool id, AppSync endpoint, etc.) automatically, and the frontend just calls `Amplify.configure(outputs)` with it. Don't invent a manual `.env` scheme for these values — that's not how Amplify Gen 2 works, and it would fight the framework rather than use it. Do add `amplify_outputs.json` to `.gitignore` (it's environment-specific, regenerated per sandbox/branch deploy, not committed).
