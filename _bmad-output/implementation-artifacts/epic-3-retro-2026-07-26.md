# Epic 3 Retrospective: Draw & Orientation Guide

**Date:** 2026-07-26
**Participants:** Tony (Project Lead), Amelia (Developer, facilitating), Winston (Architect), Murat (Test Architect), John (Product)

## Epic Summary

- **Completed:** 8/8 stories (100%) — 3.1, 3.2, 3.3, 3.8, 3.4, 3.5, 3.6, 3.7
- **Scope delivered:** FR6–FR10 — an authenticated user describes their situation, draws cards, and receives a real LLM-generated Orientation Guide through a durable asynchronous execution, bounded by atomic daily/monthly cost controls and tracked through an owner-readable Session.
- **Review depth:** tracked by review rounds/findings rather than story points in this project. Story 3.8 (durable-execution rewrite) was the clear outlier — an initial pass plus a dedicated "runtime and infrastructure re-review" plus a dedicated "backend tests re-review," spanning roughly five days. Story 3.2 (first LLM/payment-gate integration) was second-heaviest at three review rounds. 3.1, 3.5, 3.6, 3.7 were consistently clean, single-pass reviews.
- **Technical debt:** roughly two dozen items opened into `deferred-work.md` across the epic.
- **Production incidents:** zero — but every deploy so far has been to a single ephemeral sandbox (local Vite + local browser only). No persistent `staging`/`main` environment exists yet; none of Epic 3's reservation/durable-execution/alerting code has been exercised outside that one sandbox. Full public deployment (a real reachable domain) is a deliberate future correct-course Tony already has in mind, not a gap in this epic.
- **Credential/content hygiene:** held perfectly across all 8 stories — zero regressions on the "never commit live Context/Guide/credentials" rule.
- **Defining technical surprise:** AppSync's hard, non-configurable 30-second response ceiling, discovered via 3.2's live verification (real generations measured 30.6–30.7s). This forced the Story 3.8 mid-epic architecture pivot.

## What Went Well

- **The Story 3.8 correct-course pivot.** Rather than patch around the AppSync ceiling story by story, the team stopped, wrote a formal sprint-change proposal, got explicit approval, rebuilt the generation boundary as a starter-Lambda-plus-durable-worker split, and structurally prevented drift by freezing Story 3.3 in review and gating 3.4/3.5/3.7 behind 3.8's completion. Tony confirmed this put the epic "totally back on track."
- **Proactive operational hardening in 3.8's re-review** — the reconciler for stuck `PENDING` Sessions, the dead-letter queue, and the alarm-backed runbook were all built during review, before any real incident occurred.
- **Composition discipline held for the whole epic** — `OrnamentalDivider` (built once in 3.1, reused in 3.3), `SpreadSelector`'s additive props instead of a fork, a byte-exact reused secondary-button class string across four components. The frontend stories (3.1, 3.3, 3.4, 3.7) were consistently the cleanest-reviewed work in the epic.
- **The Task-0 pre-flight + "Pre-dev prerequisites (Tony)" pattern** was adopted with 100% consistency across all 8 stories.
- **The product actually works.** Tony's own words: "I got answers I could use in real life! The app works!" — the whole reservation/durable-execution/grounding pipeline is landing as genuinely useful output, not just a technically-correct system nobody would want to use.

## Challenges

- **The Tavily secret propagation gotcha recurred at least three times** (3.3, 3.8, 3.5) — Amplify leaving a stale secret value on a redeployed Lambda, producing HTTP 401s each time. Worked around every time (a mandatory alias-qualified post-deploy probe is now standing process), but the underlying flakiness was never actually fixed. Tony has a future correct-course planned to move the Tavily secret to AWS Secrets Manager directly, after Epic 4.
- **"Marked done but not actually pushed" recurred inside Epic 3 itself**, despite being named in Epic 1's retro and supposedly closed by Epic 2's tightened Definition of Done: 3.4's Task 0 found ~2,270 uncommitted lines from 3.8's re-review that its own record claimed was pushed; then 3.4's own second review round opened the same way. The Task-0 safety net caught it every time — nothing was ever lost — but the root behavior (self-attested "committed and pushed" as prose, never mechanically verified) kept slipping.
- **Mutation-survivable tests**, concentrated in 3.4's later review rounds and recurring in 3.8's durable-lifecycle tests — tests that pass but can't actually fail against a wrong implementation.
- **Two genuine mid-flight re-scopes** beyond 3.8's headline pivot: 3.4 HALTed on a real contradiction between the frozen task spec and the actual UX requirement, resolved live by Tony's on-the-spot decision to persist the redraw draft in localStorage. 3.7 was proactively shrunk at story-creation time when the dev agent discovered 3.1 had already forward-delivered the whole feature.
- **Tavily's actual perceived value is uncertain.** Tony reports the grounded-vs-ungrounded difference "doesn't matter much either way" day-to-day — worth noting given how much operational pain the integration has caused. Not urgent, but a real tension worth revisiting if the pain resurfaces.
