# Spine Pair Review — tarot-spa (Systems Thinking Tarot)

## Overall verdict

This is a strong, disciplined spine pair for a hobby-tier release — section order is canonical, brownfield grounding is real (tokens traced to actual Tailwind classes in `src/components`), and the two PRD-sourced UJs carry through verbatim with matching climax/resolution beats. The gaps are narrow and mostly at the seams between the two files: one frontmatter color token (`on-primary`) is never narrated in prose, two components used in EXPERIENCE.md (`Spread Selector`, the Grant-Key copyable-code element) have no DESIGN.md visual row, a naming drift between "Card container" and "Card Display," and one invented UJ (UJ-3) that isn't flagged as non-PRD-sourced despite reusing the PRD's UJ-numbering convention. None of these block downstream work, but a story-dev consumer would hit a short pause on each.

## 1. Flow coverage — adequate
Checked every UJ named in prd.md §2.3 (UJ-1 Erica, UJ-2 Maya — the only two defined) against EXPERIENCE.md Key Flows, plus every FR (FR-1–FR-12) against IA/Component/State coverage where no Key Flow exists.
### Findings
- **medium** EXPERIENCE.md adds a third flow, "UJ-3 — Priya" (EXPERIENCE.md:128), reusing the PRD's `UJ-` numbering convention for a journey that does not exist anywhere in prd.md §2.3 (only UJ-1 and UJ-2 are defined there). The memlog documents this as a deliberate addition to cover the public-landing surface, but the flow itself carries no in-file marker distinguishing it from a PRD-sourced UJ. *Fix:* label it something that can't be confused with a PRD ID (e.g. "New Flow — Priya" or "UJ-3 (new, UX-added)") so a downstream reader diffing against prd.md doesn't go looking for a UJ-3 that isn't there.
- **medium** The Orientation Guide Results screen's content structure — "cards → Current Events → correlation → guidance" (EXPERIENCE.md:26, 117) — doesn't map cleanly onto FR-8's actual 5-part Guide structure (prd.md:169: pattern-in-situation, what's-missing, framing-challenge, counterintuitive-implication, better-questions) or use the Glossary term "Lens" (prd.md:64) at all. "Correlation" is a UX-invented label with no source anchor. *Fix:* either cite which FR-8 sub-parts "correlation" and "guidance" each bundle, or adopt Lens/Guide language directly so a component builder has an unambiguous mapping.
- **low** FR-1/FR-2/FR-3/FR-11/FR-12 (sign-up, grant-key, admin) have no dedicated Key Flow — only IA/Component/State coverage. This is consistent with the memlog's explicit decision (.memlog.md:21) not to write narrative journeys for these, and the coverage that exists (Invite Key Field states, Grant Key Action rules, Admin Metrics row) is adequate for FRs that aren't UJs. Flagging only because a downstream reader expecting 1:1 FR-to-flow coverage should know this was a conscious scope call, not an oversight.
- **low** FR-11's required dashboard metrics (users by generation, Session count, Daily-Orientation-Limit hit-rate, spend-to-date vs. FR-10 ceiling — prd.md:220-227) are not enumerated anywhere in EXPERIENCE.md's "Admin Metrics + Mint Key" row (EXPERIENCE.md:61), which only says "plain metrics list/table." Consistent with the explicit "ugly but functional, no design polish" directive (DESIGN.md:147), so likely intentional, but a story-dev consumer building the actual dashboard has to go back to the PRD for the metric list.

## 2. Token completeness — adequate
Extracted all 17 frontmatter `colors`, 6 `typography` roles, 5 `rounded` scale entries, 3 `spacing` tokens, and 6 `components`. Checked each against its Colors/Typography/Layout & Spacing prose story, and checked the one `{path.to.token}` reference in EXPERIENCE.md (`{colors.primary}`, EXPERIENCE.md:81) resolves — it does.
### Findings
- **medium** `on-primary: '#ffffff'` (DESIGN.md:18) is defined in frontmatter and consumed correctly in `components.button-primary.text` (DESIGN.md:71), but the Colors prose section (DESIGN.md:101-111) never narrates it — the `primary`/`primary-strong` bullet (DESIGN.md:108) covers the button fill but not its text color. Every other color token gets a "why it exists, where it's used" sentence; this one doesn't. *Fix:* fold a clause into the `primary` bullet, e.g. "...`on-primary` (white) is the fixed text/icon color on any primary-fill surface."
- **low** `primary-container: 'rgba(49, 46, 129, 0.6)'` (DESIGN.md:19) uses an rgba() value where the spec's stated convention is hex strings (design-md-spec.md:15: "Values are hex strings"). Functionally fine (it documents a real alpha-blended existing treatment) but technically off-convention — worth a one-line note in the frontmatter comment if a stricter downstream parser ever expects hex-only.
- **low** Contrast ratios are never stated for load-bearing combinations (e.g. `on-primary` white on `primary-strong` indigo-600 button fill; `error` red-400 on `surface` gray-950; `inverted-accent` amber on dark background for pattern text). EXPERIENCE.md's Accessibility Floor (EXPERIENCE.md:87-94) explicitly defers to "no formal WCAG audit... hobby-tier stakes," which makes this a defensible, disclosed omission rather than a silent gap — flagging only because the rubric calls it out as expected for load-bearing combos.
- **low** Typography roles `display`, `headline`, `title`, `body` (DESIGN.md:24-45) get no individual usage-story in the Typography prose (DESIGN.md:113-117) — only `body-essay` and `label-caps` (the two new-for-this-release roles) are narrated. Likely acceptable brownfield economy since the rest are pre-existing and unchanged, but it's a thinner treatment than Colors gets for its equally-pre-existing tokens.

## 3. Component coverage — thin
Extracted every component name referenced anywhere: DESIGN.md.Components lists 5 (Button, Card container, Input, Position label, Ornamental divider); EXPERIENCE.md.Component Patterns lists 10 (Card Display, Ornamental Divider, Context Textarea, Spread Selector, "Help Me Orient" CTA, Redraw Actions, Invite Key Field, Request Access Form, Grant Key Action, Admin Metrics + Mint Key). Cross-checked each direction.
### Findings
- **high** `Spread Selector` (EXPERIENCE.md:55, used on 3 surfaces: Context Entry, authenticated Quick Draw, public Quick Draw) has zero visual-spec row in DESIGN.md.Components (DESIGN.md:133-139) — not even a "carried forward unchanged, no delta" note. The one near-hit is DESIGN.md:135's Button bullet, which mentions "`SpreadView`/`SpreadSelector` button treatment" in passing, but that's describing button styling *inside* the selector, not the selector's own visual spec (layout, selected-state treatment, etc.).
- **medium** `Grant Key Action`'s output — "one onward Invite Key rendered as a copyable code" (EXPERIENCE.md:60) — has no corresponding visual spec anywhere in DESIGN.md. How a generated key/code is rendered (monospace treatment? background chip? copy-icon placement?) is new UI with no token mapping.
- **medium** Naming drift: DESIGN.md's visual-spec heading is "**Card container**" (DESIGN.md:136) while EXPERIENCE.md's behavioral row is "**Card Display**" (EXPERIENCE.md:52) — both are describing the same real `CardDisplay` component (both rows name it literally), but the section headers themselves aren't identical strings, which breaks a clean name-based cross-reference.
- **low** `Position label` has a DESIGN.md visual row (DESIGN.md:138) but no corresponding EXPERIENCE.md Component Patterns row — it's implicitly folded into "Card Display"'s "unchanged from the existing app" description (EXPERIENCE.md:52) rather than called out on its own. Low severity since it's explicitly carried-forward-unchanged behavior.
- **low** "Admin Metrics + Mint Key" (EXPERIENCE.md:61) has no list/table visual spec in DESIGN.md — defensible given the explicit "ugly but functional... reusing existing components as-is" directive (DESIGN.md:147), so likely intentional non-invention rather than an oversight.

## 4. State coverage — adequate
Walked all 8 IA surfaces (Public Landing, Sign Up, Context Entry, Orientation Guide Results, Quick Draw, Rate-Limited Intake, Grant Invite Key, Admin Dashboard) against the 9-row State Patterns table.
### Findings
- **medium** `Grant Invite Key` has no row at all in State Patterns (EXPERIENCE.md:63-75). Its "already used" state is described only inline in Component Patterns ("Disabled/hidden once already used," EXPERIENCE.md:60), and no failure state (mint/generation failure) is defined anywhere for this surface.
- **medium** No explicit access-control state is defined for what happens when a Second-Gen account navigates directly to `Grant Invite Key`, or a non-admin account navigates to `Admin Dashboard` — both are gated only via the IA "Reached from" column ("First-Gen accounts only" / "Tony's admin-flagged account only," EXPERIENCE.md:29-30) rather than a stated behavior (hidden from nav vs. blocked screen vs. redirect). FR-2's testable consequence — "Second-Gen Accounts have no path (UI or otherwise)" (prd.md:97) — implies this needs an explicit UX answer, analogous to the reference example's "Permission denied... surface hidden from sidebar, no blocked screen" pattern (experience-example-shadcn.md:64).
- **low** No state is defined for direct/bookmarked reload of Orientation Guide Results (cold-load of a non-persisted generated screen), or for Sign Up's success transition (failure states are enumerated; the success path to authenticated home isn't stated as its own row, unlike Request Access's success row which does get one).

## 5. Visual reference coverage — n/a (as expected)
`mockups/`, `wireframes/`, `imports/` are all empty — confirmed via `ls`. EXPERIENCE.md's IA section (EXPERIENCE.md:32) forward-references three mockup files ("`mockups/context-entry.html`," etc.) explicitly marked "(to be added at Finalize)," which is the correct way to flag not-yet-created visual references — no dangling/broken links to report.

## 6. Bloat & overspecification — strong
DESIGN.md's brownfield cross-mapping (token name alongside the real Tailwind class, e.g. "`section-gap` (48px, roughly the existing `py-12`/`mb-12` usage)," DESIGN.md:121) reads as necessary grounding for a project with "no custom design-token layer in code" (DESIGN.md:3), not restatement. EXPERIENCE.md's Key Flows stay terse and decision-relevant (every narrative beat ties to a UJ detail already in the PRD — the "four-star lemonade" line, the Resources-card reframe — no invented scene-setting). No prose found where a table would clearly work better; Do's and Don'ts uses bullets rather than the reference examples' table format, which is a stylistic choice the spec permits. No sections found that a downstream consumer wouldn't read.

## 7. Inheritance discipline — adequate
`sources` frontmatter (EXPERIENCE.md:4-9) resolves cleanly to all 5 files. UJ-1/UJ-2 content and IDs carry through verbatim from prd.md §2.3, including the exact quoted lines ("four-star lemonade...", "What's the minimum viable complexity?"). FR citations (FR-8, FR-9, FR-5, etc.) all resolve to real PRD FRs. The invented "UJ-3" (see §1) and the "correlation" terminology (see §1) are the two real inheritance breaks — both are cases where EXPERIENCE.md introduces vocabulary that looks source-derived but isn't. The "Card container"/"Card Display" naming drift (see §3) is the one place component names aren't byte-identical across the two files.

## 8. Shape fit — strong
DESIGN.md section order — Brand & Style, Colors, Typography, Layout & Spacing, Elevation & Depth, Shapes, Components, Do's and Don'ts — matches the canonical order exactly (DESIGN.md:97-147). EXPERIENCE.md includes all required defaults (Foundation, IA, Voice and Tone, Component Patterns, State Patterns, Interaction Primitives, Accessibility Floor, Key Flows) in the same order as the shadcn reference example, plus both required-when-applicable sections correctly triggered and justified: Inspiration & Anti-patterns (real rejects — New Age iconography, admin charts, survey/nudge UI, hard rate-limit rejection — all present, EXPERIENCE.md:100-107) and Responsive & Platform (bonus for a single-surface app, adds real content: shared breakpoint set, the hardcoded `/tarot-spa/` base-path constraint). No invented sections; no defaults dropped without reason.
