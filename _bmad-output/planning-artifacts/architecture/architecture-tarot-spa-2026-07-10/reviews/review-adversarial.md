# Adversarial Incompatibility Review — tarot-spa Architecture Spine

## Overall verdict

The spine's atomic-counter language (AD-6) sounds precise but is actually underspecified at exactly the point that matters — whether the check happens before or after the expensive call — which means two implementers building "to the letter" can produce one build that truly gates concurrent requests and one that doesn't, silently reopening the PRD review's flagged race. Several other ADs have binds lists that quietly exclude an entity they visibly govern in practice (MonthlySpend under AD-9, InviteKey under AD-6), leaving real seams for divergent, individually-compliant implementations. None of these are exotic; each is the kind of gap an AI coding agent building two Lambdas from this spine, one story at a time, would fall into without ever violating a written Rule.

## Findings

- **critical** AD-6's Rule says the atomic increment-and-check happens "as part of each Orientation Guide request," but the Consistency Conventions table says the increment "only happens on confirmed successful Orientation Guide completion" — i.e., *after* Tavily+Bedrock finish. Implementer A reads this as pre-flight gating: atomically check-and-increment DailyUsage *before* calling Tavily/Bedrock (true real-time gate), then needs an unspecified atomic decrement-on-failure path to honor "never increments on a failed call." Implementer B reads it literally: do a cheap plain `GetItem` check before the expensive calls (to short-circuit obviously-over-limit users), then atomically increment only after confirmed success. Implementer B's plain pre-check is not atomic with the increment, so N concurrent requests near the boundary all pass the check, all run to completion, and all increment afterward — reproducing exactly the "duplicate/near-simultaneous requests race the limit check" failure the PRD edge-case review already flagged (review-edge-case.md, prd.md:158-169/187-196). Both implementations satisfy AD-6's words. *Fix:* a new/tightened AD-6 clause that explicitly names the two-phase protocol — atomic pre-flight reservation (check-and-increment before the LLM call) plus an atomic compensating decrement on confirmed failure — and states that the "increment only on success" language refers to net effect after rollback, not to when the atomic operation fires.

- **critical** MonthlySpend does not appear in AD-9's `Binds` list ("Account, Session, DailyUsage records; Admin Dashboard queries and key-minting") even though it is the one model that is structurally an all-accounts aggregate with no owning identity. Implementer A, generalizing AD-9's owner-based pattern to "every model gets an owner rule unless told otherwise," applies owner-based auth to MonthlySpend — which breaks immediately, since no single Cognito identity legitimately "owns" a cross-account monthly total, and admin reads become either impossible or require a per-record ownership hack AD-9 explicitly forbids ("never by relaxing per-record ownership"). Implementer B, noticing the gap, has the usage-counter Lambda write MonthlySpend via a raw DynamoDB SDK call under its execution IAM role, bypassing AppSync/Amplify Data auth entirely, and exposes it to the Admin Dashboard through a separate, unauthenticated-at-the-model-level custom query — a hole, since nothing pins down that this bypass path is admin-group-gated the same way AD-9 requires for "Admin Dashboard queries." *Fix:* add MonthlySpend explicitly to AD-9's binds with its own rule ("no owner-based rule; admin-group-read-only via Amplify Data auth; write path restricted to the usage-counter Lambda's IAM role, never exposed as a client-writable field").

- **critical** Nothing in the spine requires the invite-key-mint Lambda (AD-4: one capability, no shared abstraction, so this check lives only in that Lambda's own handler.ts) to verify the requesting account is First-Gen before minting an onward key. AD-9's admin-group/owner split governs *who can read/write which records*, not the FR-1–3 business rule that only First-Gen accounts may generate one onward key. Implementer A guards mint-eligibility by checking "has this account already issued a key" (a duplicate-submit guard, per the PRD review's FR-2 concern) but never checks `generation`/provenance at all. Implementer B guards it correctly. Under Implementer A's build, a Second-Gen account that has never minted a key (because it's never been offered the button in the UI) can call the mint mutation/Lambda directly and succeed, since "hasn't generated one yet" is true for every Second-Gen account by definition — silently defeating the two-generation cap the ER diagram's "grants onward (First-Gen only)" annotation asserts but no AD actually states as an enforceable Rule. *Fix:* a new AD (or AD-9 amendment) stating the invite-key-mint Lambda must atomically verify `account.generation == First-Gen AND account has not already minted an onward key` as a single conditional check, and that this check is enforced server-side in the Lambda, never assumed from UI affordance.

- **high** AD-6's atomicity guarantee ("atomic conditional UpdateItem") is scoped in its own `Binds` line to "FR-9 (Daily Orientation Limit), FR-10 (aggregate monthly budget ceiling)" only — it does not bind InviteKey redemption (FR-1) at all, and AD-8 (data model/composite keys) says nothing about an InviteKey status field or a conditional-write requirement on redemption. Implementer A redeems a key with a plain read-then-write (`GetItem` status check, then `UpdateItem` to `redeemed`), satisfying every literal Rule in the spine. Implementer B uses a `ConditionExpression: status = :unredeemed` on the redemption UpdateItem. Both are spine-compliant; Implementer A's build reopens the exact double-redemption race the PRD edge-case review already flagged (review-edge-case.md, prd.md:80-89) — two concurrent redemptions of one key create two Accounts. *Fix:* extend AD-6 (or add a new AD) explicitly requiring InviteKey redemption to use the same atomic-conditional-UpdateItem pattern, keyed on `status`, as a first-class binding alongside DailyUsage/MonthlySpend.

- **high** DailyUsage is a count and MonthlySpend is a dollar figure, but AD-6 treats them with one undifferentiated Rule ("DailyUsage and MonthlySpend are enforced via an atomic conditional UpdateItem"). DailyUsage's increment amount (1) is known pre-flight; MonthlySpend's increment amount (real Bedrock token cost) is only known *after* the Claude Opus call completes. Implementer A increments MonthlySpend by a fixed estimate (e.g., the memlog's ~$0.03/request figure) pre-flight so the budget ceiling actually gates in real time, then never reconciles against actual billed cost. Implementer B increments MonthlySpend by the real post-call cost, meaning the $30/month ceiling (AD-6/FR-10) is purely a post-hoc ledger with no real-time blocking power for the request that pushes spend over budget — directly undermining AD-6's stated purpose ("relying on AWS Budgets alone... lags too far behind real time to gate individual requests": Implementer B's design has the same lag problem AD-6 exists to prevent). Neither AD-6 nor AD-13 specifies which. *Fix:* tighten AD-6 to state explicitly whether MonthlySpend's increment value is a fixed per-request estimate checked pre-flight, or an actual-cost figure reconciled post-flight, and if the latter, what (if anything) gates the ceiling in real time.

- **high** AD-6's Rule says "a failed Current-Events/LLM call does not increment either counter," while AD-14 says a Tavily timeout still "proceeds to the Claude Opus generation call" and produces a (ungrounded) Guide rather than failing the request. It is genuinely ambiguous whether a Tavily *timeout* is "a failed Current-Events... call" (→ Implementer A's reading: don't increment, since the Current-Events leg literally didn't succeed) or whether only an *outright request failure* triggers the no-increment carve-out, with an ungrounded-but-delivered Guide counting as a normal completion (→ Implementer B's reading: increment as usual, since AD-14 says the request itself "proceeds," it doesn't fail). Implementer A's build creates a free, uncounted-request path: repeatedly triggering (or waiting out) the 20s Tavily timeout yields unlimited ungrounded Guides that never touch DailyUsage or MonthlySpend, defeating both FR-9 and FR-10. *Fix:* add an explicit clause (to AD-6 or AD-14) stating that a Tavily-timeout-then-ungrounded-Guide is a confirmed successful Orientation Guide completion for counter purposes, and only an outright Tavily *or* Bedrock failure (not a timeout-with-fallback) qualifies for the no-increment carve-out.

- **medium** AD-8 fixes the model set but adds no field to Account for tracking "has this First-Gen account already minted its one onward key," and no AD specifies the mechanism. Implementer A tracks eligibility by querying the InviteKey table for `issuerAccountId == this account` (query-then-insert, non-atomic — a double-click or duplicate-submit races into two onward keys minted from one account, per the PRD edge-case review's FR-2 concern). Implementer B adds an `onwardKeyGenerated: boolean` field to Account and mints via a conditional UpdateItem on that flag. Both comply with AD-8 ("no additional top-level models" is preserved either way — a field isn't a model) and AD-4, yet only one closes the race. *Fix:* AD-8 (or a new AD) should specify that onward-key-mint eligibility is tracked via a boolean/atomic field on Account, checked-and-set via the same conditional-UpdateItem pattern as AD-6, not derived by querying InviteKey.

- **medium** AD-4 says Lambdas call "AppSync/DynamoDB... directly," which is ambiguous between (a) invoking the Amplify Data client against AppSync, subject to the owner-based/admin-group auth rules AD-9 defines, and (b) calling the raw DynamoDB SDK under the Lambda's IAM execution role, which bypasses AppSync's authorization layer entirely. This ambiguity compounds Finding 2 (MonthlySpend auth) and also affects DailyUsage/Account writes from the usage-counter and invite-key-mint Lambdas: Implementer A routes all writes through the authorized Amplify Data client (owner rules apply, but a Lambda acting on behalf of a *different* user's identity — e.g., minting a key that another account will redeem — may not have a well-defined "owner" context at write time); Implementer B routes all Lambda-originated writes via raw DynamoDB SDK/IAM, making AD-9's owner-based rule purely a client-side-mutation-path control that every Lambda-initiated write silently bypasses. The spine never states which. *Fix:* add a clause to AD-4 or AD-9 specifying whether Lambda-to-DynamoDB writes go through the Amplify Data authorized client or direct IAM-scoped DynamoDB calls, and if the latter, that AD-9's owner-based rule is understood to constrain only client-originated GraphQL mutations, not server-side Lambda writes.

- **low** AD-13 says the usage-counter Lambda reads the single Config item "on every request," but doesn't specify whether one Config read is reused for both the DailyUsage and MonthlySpend checks within a single request, or whether each check re-reads Config independently. Given Finding 1's two-phase (check, then act) ambiguity is already unresolved, this is a secondary, lower-stakes fork: Implementer A reads Config once per request and reuses `dailyLimit`/`monthlyBudget` for both checks (consistent within-request view); Implementer B re-reads Config before each of the two independent conditional updates, so a same-request admin edit mid-flight (unlikely but possible with concurrent admin activity) could apply the old limit to one counter and the new limit to the other. *Fix:* note in AD-13 that Config is read once per request and both counter checks within that request use the same snapshot.
