# Architecture Spine Rubric Review — tarot-spa

## Overall verdict

The spine is well-formed mechanically (valid Mermaid, contiguous AD IDs, source tree matches the named ADs) and does real work resolving the PRD's genuinely open questions (AD-13 config, AD-14 Tavily timeout, AD-15 SES). But it has one critical coverage gap — it silently drops the invite-key redemption concurrency/atomicity/abuse risks that the PRD explicitly delegated to architecture — plus a real, unreconciled contradiction between AD-2's locked-in GH-Pages base path and AD-11's move to Amplify Hosting. Not ready to exit the Reviewer Gate as-is; fixable with two new ADs and one clarifying edit.

## Findings

- **critical** FR-1 (Invite Key redemption / Account creation) has no AD at all, despite the PRD explicitly carrying three edge-case findings forward "into the architecture doc" (prd.md §12, citing `review-edge-case.md`): (1) concurrent redemption of the same key creating two Accounts, (2) partial-write failure between Cognito signup and the key-redeemed write (orphaned Cognito user / stuck key state), (3) the same person redeeming multiple keys to bypass the per-Account Daily Orientation Limit. AD-6 gives DailyUsage/MonthlySpend an atomic-conditional-update pattern for exactly this class of problem; no equivalent rule exists for InviteKey redemption, and no Lambda/trigger for it appears in the source tree (only `invite-key-mint`, which is the *minting* side, not redemption). Two independently-built units could easily diverge here — one might do a naive read-then-write (races), another a saga — and one is silently vulnerable to double-redemption. *Fix:* add an AD binding FR-1 that specifies (a) the redemption path as an atomic conditional `UpdateItem` on InviteKey status (unredeemed → redeemed) mirroring AD-6's pattern, (b) which side is authoritative/rolled-back-first when Cognito signup and the key-redeemed write disagree (a Cognito post-confirmation trigger doing the key-redeem write is the natural idiomatic Amplify answer), and (c) whether same-identity multi-key redemption is prevented and how (e.g., verified-email uniqueness check at redemption). Add the corresponding Lambda/trigger to the source tree.

- **high** AD-2 ("the frontend remains... `vite.config.js`'s `base: '/tarot-spa/'` is respected by every new route... this release adds") is not reconciled with AD-11 + the Structural Seed diagram, which show the frontend served from Amplify Hosting in both `staging` and `main`/prod — and the memlog (line 10) records "Amplify hosting replaces GH Pages, not supplements it" as an ADOPTED constraint. `/tarot-spa/` is a GH-Pages-project-page artifact (serving under `username.github.io/tarot-spa/`); Amplify Hosting has no equivalent default subpath convention. Locking AD-2's Rule in as-is, unrevisited, risks exactly the failure mode AD-2 itself exists to prevent ("naive absolute paths or router configs that 404 once deployed") — just from the opposite direction (a stale subpath assumption surviving a hosting migration that no longer needs it). *Fix:* add a line to AD-2 (or a new AD) that explicitly states whether Amplify Hosting will be configured to preserve `/tarot-spa/` (e.g., custom domain + path rewrite, for old link continuity) or whether the base path is dropped to `/` as part of the migration — this is a real decision, not a carry-forward.

- **medium** FR-11 (Admin Dashboard aggregate metrics: users-by-generation, Session counts, Daily Orientation Limit hit-rate, spend-to-date) has no stated computation mechanism. AD-10 says *what* it must show (aggregate-only, no raw content) and AD-9 says *who* can access it, but nothing says *how* the aggregates are produced — direct Amplify Data list queries from the frontend, or a dedicated Lambda (consistent with the "thin Lambda per capability" paradigm every other capability in this spine follows, per AD-4)? This is a real dimension left silent at feature altitude: one implementer could hand-roll client-side aggregation over paginated list queries, another could add a 5th Lambda — a visible divergence. *Fix:* add a short AD (or extend AD-10) naming the mechanism, and if it's a Lambda, add it to the source tree alongside the other four.

- **medium** The Structural Seed's ERD treats `SESSION`→`MONTHLY_SPEND` as an aggregation edge but has no equivalent `SESSION`→`DAILY_USAGE` edge, even though AD-6 states both counters increment together "as part of each Orientation Guide request" (the same underlying event). This asymmetry is internally inconsistent modeling — either both counters should show their driving relationship to SESSION, or neither should, given they're populated by the identical atomic-update-on-completion event. As drawn, a reader could reasonably (and wrongly) infer DailyUsage is derived differently than MonthlySpend. *Fix:* add `ACCOUNT ||--o{ SESSION` (already present) plus either drop the SESSION–MONTHLY_SPEND edge in favor of a note in AD-6, or add the matching SESSION–DAILY_USAGE edge for symmetry.

- **low** AD-15's claim about Amazon SES sandbox-mode behavior (recipient-verification required until production access is requested) is asserted in both the spine and the memlog decision entry without an explicit "(version) Web-verified" memlog citation — unlike the Amplify Gen 2, Bedrock model-lineup/pricing, grounding-options, and Tavily-pricing claims, which all carry explicit dated web-verification lines. SES sandbox behavior is stable/well-known enough that this is a low-risk gap, but it's an inconsistency in the memlog's own evidentiary standard. *Fix:* either add a one-line web-verification memlog entry for SES sandbox behavior, or note in AD-15 that this is treated as common-knowledge AWS behavior rather than independently re-verified.

- **low** AD-11's Rule text (staging/main branch-per-environment) doesn't itself state that the existing `.github/workflows/deploy.yml` → GitHub Pages pipeline is retired — that's only inferable from the Structural Seed diagram (which shows only Amplify Hosting, no GH Pages) plus the memlog's separate "Amplify hosting replaces GH Pages, not supplements it" line. `project-context.md` flags this exact decision ("Multiuser work will require extending this pipeline or adding a separate backend deployment path — an architecture-level decision") as one the architecture is explicitly responsible for making explicit. *Fix:* add one sentence to AD-11's Rule making the deploy.yml/GH Pages retirement explicit rather than diagram-only.

- Nothing under Deferred is secretly load-bearing — **pass**: reviewed all 8 Deferred bullets against the two-generation cap, admin scope, timezone, retention/deletion items — none create cross-unit divergence risk. FR-1 (redemption mechanism/atomicity) and FR-11 (aggregate-metrics computation mechanism) are the two FRs with real architectural weight that don't land anywhere.

Flagged instead (medium finding above) for an internal-consistency issue: DAILY_USAGE gets no equivalent edge from SESSION despite being populated by the same event per AD-6.
- AD IDs contiguous, non-duplicated AD-1–AD-15 — **pass**: verified all 15 present exactly once, no gaps.
- Source tree matches ADs/Stack (Lambdas named in AD text appear in the tree, and vice versa) — **pass for what's named, gap for what's silently absent**: all 4 tree Lambdas (`orientation-guide`, `invite-key-mint`, `usage-counter`, `request-access`) map 1:1 to their ADs and FR comments with no orphans in either direction. But per the critical/medium findings above, FR-1's redemption logic and FR-11's metrics computation have no function anywhere, named or unnamed — the tree is consistent with the ADs but the ADs themselves are incomplete.
