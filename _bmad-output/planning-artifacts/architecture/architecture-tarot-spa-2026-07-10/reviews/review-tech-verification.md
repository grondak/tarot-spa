# Tech Currency & Fit Verification — tarot-spa Architecture Spine

## Overall verdict

The spine's load-bearing technology claims hold up: independent re-verification today confirms Amplify Gen 2's data-layer approach, current Bedrock Claude Opus availability and pricing, Tavily's free-tier/pricing, and Amazon SES sandbox behavior all match what's stated, and none have drifted since the memlog's 2026-07-10 research (expected, given the one-day gap). The frontend Stack versions (React/Vite/Tailwind/ESLint) are exact matches to the project's own `package.json`, which is stronger evidence than a web search. The one real gap is a Bedrock implementation detail — current-generation Claude Opus models on Bedrock require an inference-profile identifier rather than a bare model ID in many regions/versions — that neither the spine nor the memlog addresses, and a handful of AD-13/AD-15/AD-11-adjacent facts were asserted without a memlog "Web-verified" entry (now independently confirmed correct, but the process gap is worth naming).

## Findings

- **medium** AD-5 and the Stack table describe the LLM call only as "Claude Opus (via Bedrock) — Opus 4.x family, Bedrock Converse API," with no mention that current-generation Opus models are invoked differently depending on version/region: Opus 4.5 and 4.6 require an inference-profile ARN/ID (not a bare foundation-model ID) on Bedrock, and Opus 4.7/4.8 require a cross-region inference profile (`us.`/`eu.`/`global.` prefix) in most regions, only working as a direct model ID in select regions. This is an implementation detail, not a spine-level decision, but it's a real gotcha the `orientation-guide` Lambda will hit on its first Bedrock call, and it isn't flagged anywhere (spine, memlog, or Deferred). *Fix:* add a one-line note to AD-5 or the Stack table flagging that the Lambda must resolve the correct Bedrock model identifier (inference-profile form) for the specific Opus version and region chosen at implementation time — or add it to Deferred as an implementation-time detail to confirm.
- **low** AD-15's description of Amazon SES sandbox behavior (recipient address must be verified once; 200 emails/24hr and 1/sec sandbox quota) has no corresponding memlog `(version)` / "Web-verified" entry — it was asserted as a `(decision)` line, not confirmed via web search during the coaching session. Independently re-verified today and found accurate, so no actual risk, but it's an example of a fact stated as settled without the verification step the process calls for. *Fix:* none needed on the content; for future spine runs, route SES-sandbox-type factual claims through the same "Web-verified" tagging as the Bedrock/Amplify/Tavily claims got.
- **low** AD-11's claim that Amplify Hosting supports a fully isolated, password-protected `staging` branch environment has no memlog verification entry. Independently confirmed today: Amplify Hosting's `BasicAuthConfig` still supports per-branch (not just per-app) password protection via Console → Hosting → Access control or CloudFormation, so the claim is accurate. *Fix:* none needed; same process note as above.
- **low** AD-6's rationale ("AWS Budgets... billing data lags too far behind real time to gate individual requests") and AD-6/AD-8's reliance on DynamoDB's atomic conditional `UpdateItem` for increment-and-check are both asserted without an explicit web-verification step. Both describe long-stable, extensively documented AWS primitives (AWS Budgets' known billing-data delay; DynamoDB conditional writes), so the risk of drift is low, but neither is traceable to a memlog `version` entry. *Fix:* no action needed given the low volatility of these facts; flagging only per the audit's completeness requirement.
- **low** The Stack table's frontend versions (React 19.2.0, Vite 7.3.1, `@vitejs/plugin-react` 5.1.1, Tailwind CSS 4.2.0, ESLint 9.39.1) have no memlog "Web-verified" entries either, but are exact matches to `/Users/tonyreynolds/devtools/tarot-spa/package.json`'s `dependencies`/`devDependencies` — this is stronger ground truth than a web search would provide (the versions are literally what's installed), so this is not a real risk despite the missing memlog tag.
