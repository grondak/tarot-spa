# Adversarial Review — reviews prd.md + addendum.md as of 2026-07-07

## Findings

- **"Cheap as free" is a slogan, not a requirement.** No default or example value is ever given for the Daily Orientation Limit, no per-call cost estimate for Bedrock + internet search is stated, and the Bedrock model is explicitly "left open" (addendum). The document calls cost "the hardest constraint on this release" (§6) while never doing the arithmetic that would let anyone confirm the constraint is actually satisfiable. A hard constraint with no number attached isn't a constraint — it's an aspiration.

- **The Daily Orientation Limit bounds per-user spend, not aggregate spend.** FR-9 caps requests per Account per day, but nothing caps the total number of Accounts (Tony can mint First-Gen keys "on demand," FR-3/FR-13, with no stated ceiling). If the product's own success metric (SM-1: access requests validating "real legs") succeeds, Tony could end up with dozens-to-hundreds of Accounts, each independently allowed up to the daily cap — total spend scales with headcount, which the PRD never bounds. There is no aggregate cost ceiling, AWS Budget alarm, or kill-switch requirement anywhere in the document.

- **"Single LLM call" likely undercounts real cost.** FR-8 describes Draw + 3 Current Events (via "the LLM's own internet search") + Lens + Guide as "a single LLM call," but agentic tool-use/search patterns on Bedrock typically require multiple underlying model invocations per user-facing request. If the Daily Orientation Limit's cost model assumes 1 unit = 1 model call, real spend could be a multiple of what's budgeted. This directly undermines the cost claims in §6.

- **No alerting, only a pull-based dashboard.** FR-12 says Tony "can view" a dashboard refreshed "at least daily" — this is a passive, opt-in check, not a push alert. For a mechanism explicitly called the hardest constraint on the release, there's no requirement that Tony be notified if spend, hit-rate, or signups spike abnormally. A bug that defeats per-user enforcement (e.g., a race condition) could run unnoticed for a day or more.

- **The Bedrock model choice is deferred, but the cost conclusion isn't.** The addendum says "LLM is whatever, we'll get it from Bedrock," yet the PRD already asserts the architecture keeps costs "near-zero" (§6). Per-token pricing varies by an order of magnitude or more across Bedrock models; the PRD reaches its cost conclusion before making the one decision that actually determines it.

- **20-second latency target is asserted, not validated.** FR-8's Notes state 20 seconds is "acceptable end-to-end latency" for a live internet search plus a five-part structured essay generation, with no model chosen and no prototype/benchmark referenced. This is a specific, testable number stated as settled fact with nothing behind it.

- **No retry/degrade policy when Current Events search is slow or flaky, only fail/succeed.** The NFR under FR-8 says a failed search or LLM call "fails gracefully" and doesn't consume a Daily Orientation Limit unit — but doesn't say what happens on a slow-but-not-failed search, or whether a Guide can be produced without grounding if search times out. Since Current Events grounding is explicitly part of what makes the Lens land (vs. UJ-2's abstract miss), this trade-off materially affects product quality and is left to architecture by default rather than decided.

- **SM-1 doesn't actually test the hypothesis it claims to.** §2.1 JTBD frames the validating signal as "friends asking for keys unprompted," but SM-1 ("access requests via the public form per month") makes no attempt to distinguish organic/unprompted requests from friends Tony personally pitched (via his own LinkedIn article, per UJ-1's "Entry state"). The metric as specified can't tell Tony whether the demand is real pull or his own push.

- **The request-access form has no anti-abuse or dedup controls, which corrupts SM-1 by construction.** The Notes under FR-5 explicitly accept spam as tolerable ("if abused, retire the address") — but retiring the intake address kills the only channel SM-1 measures. There's also no rate-limiting or duplicate-submission handling, so the same person (or a bot, once the landing page is public) can trivially inflate "requests per month," corrupting the one metric the future paid-tier decision (§8.2) is gated on.

- **SM-3 and SM-C1 both depend on a Survey instrument that doesn't exist yet.** Both metrics are Primary/Counter-metrics defined in §9, but the exact Survey question set is listed as an unresolved Open Question (#4) in §10. The success criteria are specified before the measurement tool that produces them, and the underlying self-report distinction they both rely on — "reoriented" vs. "gave me advice I complied with" — is a subtle, almost philosophical distinction (illustrated by UJ-1/UJ-2 themselves) that ordinary respondents are unlikely to self-classify reliably.

- **Survey response volume is likely too small to support any conclusion.** The Follow-Up Nudge is a single cold email, sent once, up to 6 days after the Session, with no incentive and no second reminder if ignored (FR-10/FR-11). At a friend-circle scale (tens of users) and typical unprompted-email response rates, the absolute number of Survey responses per month could be single digits — yet SM-2 and SM-3 are presented as headline Primary metrics as if they'll be statistically meaningful.

- **The one named failure mode (UJ-2's "miss") has no pre-launch quality gate.** Half of the PRD's two illustrative user journeys is a documented failure (an abstract, ungrounded Guide that misses the user's actual details). The Notes under FR-8 wave this off as "a prompt-design problem... expect iteration post-launch" — there's no FR requiring any pre-launch eval/spot-check process (e.g., Tony reviewing a sample of real Guides against the UJ-2 quality bar) beyond waiting for aggregate Survey signal that may not arrive in meaningful volume (see above).

- **Privacy claims cover user-to-user isolation only, not data lifecycle.** §6 Privacy and the Cross-Cutting Security NFR both promise Context/Guide visibility is restricted to the creating Account — but nothing addresses retention (how long is this sensitive career/relationship data kept), deletion (can a user purge their own Context), encryption at rest, or whether content sent to Bedrock is used for model training/logging by AWS. For content the PRD itself calls "frequently... sensitive personal, career, or relationship information," this is asserted-not-required territory.

- **Tony's own operator access to sensitive data is an open question, not a boundary.** §6/§10 (Open Question #3) leaves unresolved whether Tony gets raw Context/Guide access for debugging. Until that's answered, the Security NFR's promise ("No Account can access another Account's Context...") is silent on the one party (the admin/operator, who likely has DB access regardless of app-level UI) most likely to actually see it. A privacy guarantee that doesn't scope the operator's own access isn't really a guarantee yet.

- **No breach, backup, or incident-handling requirements at all.** Given the sensitivity of the data acknowledged in §6, there is no requirement anywhere addressing backup, breach notification, or what happens if the data store is compromised or corrupted.

- **FR-13's tie to FR-5 has no audit trail.** FR-13 says Tony mints First-Gen keys "in response to approved requests from FR-5," but FR-5 explicitly creates "no account, database record, or waitlist position" (Out of Scope). There is therefore no requirement connecting an "approved request" to an actual minted key — no record of who asked, whether they already got one, or whether the request was ever actually approved versus just remembered. The approval workflow lives entirely outside any specified requirement.

- **The two-generation cap bounds chain depth, not headcount, undermining the "shallow growth" framing.** §4.1 describes growth as "deliberately shallow," but the only depth limit is on invite-chain length — the number of First-Gen keys Tony can personally mint is unbounded (FR-3), and FR-13 gives him nothing beyond a single "mint a key" button. If the product's own validation thesis succeeds (people asking for keys), Tony is left manually administering an uncapped, ungrown-into operation with zero workflow support (no bulk issuance, no request queue, no triage) — the admin model doesn't obviously scale to the very success condition the PRD is designed to detect.

- **Numbering error in §10 Open Questions** — the list goes 1, 3, 4, 5, 6 (item 2 is missing), suggesting the document was reorganized without a final proofread pass.

- **The Glossary breaks the document's own stated separation of concerns.** §0 explicitly states implementation-leaning detail (AWS choices, prompt template) belongs in the addendum, not the PRD — yet the Glossary's "Card" entry directly names an implementation symbol, `FULL_DECK`, inside the PRD itself.

- **Follow-Up Nudge emails have no consent/opt-out requirement.** FR-10 mandates an automated re-engagement email per Session with no stated unsubscribe mechanism or consent language. Low-stakes for a friend circle, but the PRD makes no requirement of it at all, and this is exactly the kind of gap that becomes a real problem the moment the user base is no longer "Tony's direct friends."

- **Monetization section gates a real decision on an ambiguous signal.** §6/§8.2 ties the future paid tier to "a real demand signal (people requesting First-Gen keys unprompted)" — but as noted above, SM-1 as specified can't actually distinguish unprompted demand from Tony's own promotional push, so the trigger condition for the one business decision that matters to Tony personally ("[NOTE FOR PM] the whole point of the exercise for Tony personally," §8.2) is measured by a metric that can't reliably detect it.
